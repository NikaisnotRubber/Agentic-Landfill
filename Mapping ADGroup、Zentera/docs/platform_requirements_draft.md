# AD Group x Zentera 平台化需求草案

## 1. 背景

目前流程由兩段資料來源與一段 notebook 整併組成：

1. AD 端
   - 透過 `AD 群組/fetch_ad_info.py` 產出 `groups_LTW_all.xlsx`
2. Zentera 端
   - 匯出 `User_Roles_*.csv`
   - 匯出 `Users_*.csv`
   - 匯出 `Server_Profiles_*.csv`
3. 分析端
   - 透過 `ddp_analysis.ipynb` 匯入 SQLite
   - 做帳號正規化、資料 join、欄位推導
   - 輸出 `ad_user_vm_mapping.xlsx`

系統化後，原則上維持既有資料流與來源責任邊界，不改變誰產出 AD Excel、誰產出 Zentera CSV。平台新增的是中間工作台，用來承接匯入後的預覽、編輯、映射與匯出。

這個流程可以完成一次性的盤點任務，但目前仍有幾個明顯限制：

- 執行依賴 notebook，重跑與維護成本高
- 規則隱含在 notebook 中，不利審核與交接
- 缺乏批次版本、執行紀錄、異常清單
- 產出是報表，不是可持續查詢的平台
- `tickets` 流程存在殘留依賴，整體可重現性不足

## 2. 平台化目標

本案的平台化目標，不是把 notebook 原封不動搬到 UI，而是在不改變原有資料流的前提下，建立一個可重跑、可追溯、可查詢，並支援預覽 / 編輯 / 匯出的內部資料平台。

核心目標如下：

1. 將多來源檔案的匯入流程標準化
2. 將帳號、群組、角色、VM 的映射規則產品化
3. 保留批次版本與執行證據，提升可重現性
4. 提供工作台介面，讓使用者先預覽匯入內容，再決定是否編輯與匯出
5. 同時支援報表交付與日常查詢
6. 顯性管理異常資料，而不是只產一份最終 Excel

## 3. 產品定位

建議產品定位為：

`AD Group x Zentera 權限映射平台`

它主要回答以下問題：

- 某位 AD 使用者屬於哪些群組？
- 某位使用者對應哪些 Zentera Role？
- 某個 Role 對應哪些 VM Host？
- 某個 VM 是透過哪些群組或角色間接授權？
- 哪些資料無法成功對應，需人工追查？

## 4. 目標使用者

### 4.1 主要使用者

- IT 管理員
- AD / IAM 管理人員
- Zentera 管理人員
- 權限盤點執行人員

### 4.2 次要使用者

- 稽核人員
- 主管或專案窗口

### 4.3 不建議作為第一版目標使用者

- 一般終端使用者
- 跨部門大量匿名查詢者

原因是第一版重點應放在資料可信度與流程穩定性，不是大範圍自助服務。

## 5. 範圍界定

### 5.1 第一版納入範圍

- 上傳 AD 群組 Excel 與 3 份 Zentera CSV
- 建立批次並執行資料整併
- 檢查檔案格式與必要欄位
- 預覽原始匯入內容與正規化後內容
- 僅在最終輸出資料集提供有限度欄位編輯能力
- 執行帳號標準化、姓名修正、role-user 展開
- 產出主映射報表
- 產出異常報表
- 提供基本查詢頁面
- 保留批次歷史、執行結果、輸出檔

### 5.2 第一版不納入範圍

- 即時直連 AD 自動抓取
- 即時直連 Zentera 自動抓取
- `tickets` 流程整合
- 複雜審批流程
- 多租戶或跨組織隔離
- 對外公開 API

## 6. 核心使用情境

### 6.1 批次盤點

使用者建立新批次，上傳來源檔案，先預覽匯入內容與驗證結果，再決定是否修正資料並執行映射，最後下載主報表與異常報表。

### 6.2 日常追查

使用者輸入 AD Account、群組名稱、Role 或 Hostname，查詢該對象的完整關聯鏈。

### 6.3 異常清理

使用者查看未對應成功的帳號、Role、Host 或格式異常資料，確認是否為來源資料問題或規則缺口。

### 6.4 批次比對

使用者比較不同日期的批次結果，確認新增、移除或變更的授權關聯。

### 6.5 預覽與人工修正

使用者在不改變原始來源檔的前提下，於平台內預覽匯入資料與映射結果，並僅在最終輸出資料集階段修正少量欄位值或標記例外，再以修正後版本匯出 `ad_user_vm_mapping.xlsx`。

## 7. 功能需求

### 7.1 批次管理

- 可建立新批次
- 每個批次有唯一 `batch_id`
- 可查看批次狀態：待上傳、待執行、執行中、成功、失敗、部分成功
- 可查看批次建立人、建立時間、規則版本、輸出版本

### 7.2 檔案管理

- 支援上傳以下檔案：
  - `groups_LTW_all.xlsx`
  - `User_Roles_*.csv`
  - `Users_*.csv`
  - `Server_Profiles_*.csv`
- 驗證副檔名、檔名模式、必要欄位、sheet 結構
- 記錄原始檔名、大小、checksum、上傳時間

### 7.3 資料預覽

- 可預覽每個上傳檔案的內容摘要
- 可預覽 Excel 各 sheet 與 CSV 欄位結構
- 可顯示筆數、缺值、重複值、欄位型態異常
- 可切換查看原始內容與正規化後內容

### 7.4 資料匯入與正規化

- 將原始資料寫入系統資料庫
- 將帳號統一轉大寫
- 對 `User_Roles.Users` 執行逗號拆分，展開為一人一列
- 對 `Users` 執行欄位清洗與姓名修正
- 保留正規化前後值，供追溯

### 7.5 人工編輯

- 僅允許在最終輸出資料集階段編輯白名單欄位
- 原始資料與正規化資料一律唯讀
- 原始檔內容不可被覆寫
- 所有編輯必須記錄編輯人、時間、欄位、舊值、新值、原因
- 可區分系統推導值與人工覆寫值

### 7.6 映射與規則執行

- 依既有 notebook 邏輯執行 join
- 對應關係至少包含：
  - `users.Account = ad_members.ADAccount`
  - `role_user.User = ad_members.ADAccount`
  - `servers.Application(Server Group) = role_user.Role`
- 支援欄位推導，例如由 Hostname 推導簡短 Role
- 將推導欄位與原始欄位分開保存

### 7.7 結果查詢

- 可依以下條件查詢：
  - AD Account
  - Group Name
  - BG / BU
  - Zentera Role
  - VM Hostname
  - Host IP
- 查詢結果應可展示關聯鏈，而不是只有平面表格

### 7.8 匯出

- 匯出主映射報表
- 匯出異常報表
- 匯出批次摘要
- 匯出前可預覽最終內容
- 支援整批匯出
- 支援查詢結果局部匯出
- 第一版至少支援 `xlsx` 與 `csv`

### 7.9 異常管理

至少要能標記以下異常：

- AD 成員找不到對應 `users.Account`
- AD 成員找不到對應 `role_user.User`
- Role 找不到對應 `servers.Application(Server Group)`
- Hostname 無法推導預期欄位
- 必填欄位缺值
- 姓名修正命中 heuristic

## 8. 非功能需求

### 8.1 可重現性

- 同一批來源檔案與同一規則版本，應得到一致結果
- 不可依賴殘留 SQLite 或 notebook 執行上下文

### 8.2 可追溯性

- 任一筆映射結果都應能追溯到來源檔、來源列、規則版本

### 8.3 可審計性

- 記錄誰在何時上傳、執行、匯出
- 記錄異常與人工處理痕跡

### 8.4 可維護性

- 規則需從 notebook 中抽離為獨立程式模組
- 匯入、正規化、映射、匯出應分層實作

### 8.5 效能

- 可處理與現況同級的資料量
- 執行期間應有進度與狀態回報

### 8.6 安全性

- 檔案與查詢結果涉及 AD 帳號、姓名、mail 等資訊
- 平台須有基本登入與權限控管
- 不應讓未授權使用者下載完整資料集

## 10. UI / 交互方式建議

第一版建議採 `批次處理 + 預覽編輯工作台 + 查詢頁` 模式。

### 10.1 批次頁

- 建立批次
- 上傳 4 份來源檔
- 顯示檔案驗證結果
- 進入預覽工作台
- 啟動執行
- 顯示執行摘要
- 下載輸出檔

### 10.2 預覽編輯工作台

- 左側顯示資料來源與 sheet / 檔案清單
- 主區顯示表格預覽
- 可切換 `原始資料 / 正規化資料 / 映射結果 / 異常資料`
- 支援欄位級搜尋、篩選、排序
- 僅 `映射結果` 視圖中的白名單欄位可直接編輯
- `原始資料 / 正規化資料` 視圖僅供預覽，不可編輯
- 匯出前可先預覽最終結果

### 10.3 查詢頁

- 單一搜尋框 + 篩選器
- 支援從使用者、群組、Role、Host 四種視角切換
- 查詢結果可展開來源與映射鏈

### 10.4 異常頁

- 顯示異常類型、筆數、影響範圍
- 可依批次、帳號、Role、群組篩選

### 10.5 視覺與控件原則

第一版 UI 請對齊既有內部系統風格，採企業內網工具導向設計，而非現代展示型 SaaS 風格。

具體原則如下：

- 以空間利用率優先，避免大圓角、大留白、大型卡片式構圖
- 控件圓角應極小，建議 `0px` 到 `4px`
- 以表格、分頁、工具列、區塊標題列為主，不使用漂浮式卡片語言
- 配色對齊內部系統風格，主色採藍色系，搭配白底、淺灰底、灰色邊框
- 使用細邊框、淡分隔線、低對比底色區分模組，不靠陰影堆層
- 頁首可採橫向導覽列 + 右側工具圖示區的企業後台布局
- 內容區採高密度資訊排列，讓批次、查詢、預覽、異常能在單頁內快速切換
- 圖示應以功能辨識為主，不應成為主視覺
- 空狀態插圖可保留，但尺寸應小，不占主要工作區

### 10.6 版面風格參照

根據目前提供的內部系統畫面，建議版面語言收斂如下：

- 頂部為藍色主導覽列
- 次級導覽採 tab 樣式，而非膠囊按鈕
- 工作區以白底內容面板 + 灰色外層背景構成
- 面板之間以細線分隔，可緊密並排
- 模組標題列應固定且緊湊，包含標題、操作入口、統計資訊
- 表格、清單、摘要面板應優先使用矩形結構，不使用高圓角容器
- 整體字級偏中小，適合長時間操作與資訊掃描

### 10.7 清單頁與工作台表格模式

根據補充畫面，第一版主要工作頁建議以「工具列 + 高密度資料表」為核心模式。

- 工作台主視圖應以資料表為中心，而不是卡片或多欄資訊塊
- 表格上方應有一條緊湊工具列，集中放置：
  - 主操作按鈕
  - 批次動作下拉
  - 重新整理
  - 搜尋
  - 欄位顯示切換
  - 當前資料筆數或篩選結果統計
- 資料表應支援固定表頭，必要時支援固定左側關鍵欄位
- 列高應偏緊湊，優先支援大量資料掃描
- 欄寬以資訊密度優先，可允許內容截斷並以 tooltip 顯示完整值
- 第一欄可採多選 checkbox，方便局部匯出與批次操作
- 關鍵識別欄位可用高對比底色或描邊矩形強調，但避免大面積裝飾色塊
- 狀態欄位應以文字 + 小型色彩標記呈現，不使用膠囊 badge
- 表格內操作應以小圖示或精簡文字呈現，避免大型按鈕侵占欄寬
- 表格工具列右側可保留檢視切換圖示，例如：
  - 緊湊表格視圖
  - 欄位配置視圖
  - 匯出或版面設定入口

### 10.8 控件細節規範

依目前內部系統風格，控件細節建議如下：

- 主要按鈕採矩形或微小圓角矩形，不使用膠囊形按鈕
- 次要操作以圖示按鈕或文字按鈕呈現，尺寸緊湊
- 下拉選單、搜尋框、分頁控制、欄位切換器皆採細邊框樣式
- tab 應採平面矩形樣式，以底線、高亮底色或字色區分當前頁籤
- 選中態應以淺藍底色、藍框或藍色字體強調，不使用重陰影
- 異常態可用淡紅或淡橘底色提示，但不可讓整頁過度彩色化
- 優先等級、狀態、是否異常等欄位，建議使用小色塊、警示符號或文字顏色，而非大 badge
- 空狀態、無資料狀態、完成狀態的插圖應維持輔助角色，尺寸小且位置居中
- 分頁區、筆數統計、區間顯示應固定在表格上方或下方，避免因內容切換造成跳動
- 欄位排序、篩選、顯示切換應優先採表格原生交互，不額外包裝成複雜浮層

### 10.9 資訊架構

第一版建議的主要導覽結構如下：

- `Batches`
  - 批次列表
  - 建立批次

### 10.10 頁面骨架總則

四個主要工作頁共用以下骨架：

1. 頂部主導覽列
   - 系統名稱
   - 主功能入口
   - 全域搜尋或快捷圖示
   - 使用者資訊
2. 次級區域列
   - 當前模組標題
   - 上下文切換，例如批次、視角、篩選集合
3. 工具列
   - 主操作
   - 次要操作
   - 搜尋
   - 篩選

   - 以高密度表格或矩形面板為主
5. 詳情 / 側欄區
   - 顯示當前列的來源、異常、編輯歷史或關聯鏈

### 10.11 批次頁線框說明

#### 10.11.1 頁面目的

讓使用者管理所有匯入批次，並快速進入某一批次的工作台。

#### 10.11.2 頁面結構

- 頂部：主導覽列
- 次級標題列：
  - `Batches`
  - 批次總數
  - 最近成功 / 失敗批次摘要
- 工具列：
  - `New Batch`
  - `Upload Files`
  - `Run Mapping`
  - `Compare`
  - 搜尋框
  - 狀態篩選
- 主表格：
  - `Batch ID`
  - `Created At`
  - `Created By`
  - `Status`
  - `Files`
  - `Rows Imported`
  - `Exceptions`
  - `Last Export`
  - `Actions`
- 右側或下方詳情區：
  - 批次檔案清單
  - 驗證狀態
  - 最近執行紀錄
  - 匯出紀錄

#### 10.11.3 交互重點

- 點擊某一批次列後，進入該批次的 `Workspace`

### 10.12 預覽工作台線框說明

#### 10.12.1 頁面目的

承接單一批次的完整工作流程：預覽、檢查、映射結果檢視、有限度編輯、匯出。

#### 10.12.2 頁面結構

- 頂部：主導覽列
- 次級標題列：
  - `Workspace`
  - 當前 `Batch ID`
  - 執行狀態
  - 匯入檔案摘要
- 左側導覽樹或清單：
  - `Raw`
    - `groups_LTW_all.xlsx`
    - `User_Roles.csv`
    - `Users.csv`
    - `Server_Profiles.csv`
  - `Normalized`
    - `ad_members`
    - `users`
    - `role_user`
    - `servers`
  - `Mapped`
    - `ad_user_vm_mapping`
  - `Exceptions`
    - `missing_users`
    - `missing_roles`
    - `missing_servers`
- 主工具列：
  - `Run Validation`
  - `Run Mapping`
  - `Show Differences`
  - `Export`
  - 搜尋框
  - 欄位顯示切換
  - 視圖切換圖示
- 主資料表區：
  - 顯示當前節點的資料表
  - 支援排序、篩選、固定欄、局部選取

#### 10.12.3 交互重點

## 11. 技術方向建議

- Vue 官方文件可支撐 Vue 3 + Composition API + SFC 的 TypeScript 開發模式
- Vite 官方文件支援 Vue 專案腳手架、`vite/client` 型別、`import.meta.env` 環境變數模型
- Pinia 官方文件支援型別友好的 `state / getters / actions` 寫法，適合承接工作台狀態與查詢狀態

## 14. 最終輸出欄位白名單候選

以下為目前建議的白名單收斂方向，目的是避免工作台演變成可任意改寫來源事實的介面。

### 14.1 白名單判定原則

建議只開放以下類型欄位進入白名單：

- 交付修飾欄位
- 報表標記欄位
- 需要人工補充但不回寫來源事實的欄位

建議不開放以下類型欄位：

- 來源主鍵欄位
- join 鍵欄位
- 由來源資料直接帶入且應保持可追溯的一手欄位
- 純系統推導欄位

### 14.2 建議可編輯欄位

以下欄位較適合作為第一版白名單候選：

- `NEW VM`
  - 理由：偏向交付標記欄位，較像人工判讀或盤點註記
- `Template Name`
  - 理由：可能屬於交付補充資訊，未必能穩定由來源自動得到
- `Location`
  - 理由：偏向交付層補充欄位，適合人工修正
- `NAS Folder Name`
  - 理由：若目前非穩定來源自動產生，可視為交付層補充欄位
- `NB Hostname`
  - 理由：若此欄位主要用於交付呈現而非核心 join，可納入候選，但需再確認其來源角色

### 14.3 建議維持唯讀欄位

以下欄位不建議開放人工編輯：

- `AD Account`
- `AD Name (Chinese Name)`
- `FirstName`
- `LastName`
- `Mail`
- `BG`
- `BU`
- `Group Owner`
- `Group Name`
- `VM HostName`
- `Host IP`
- `User Roles`
- `Application`

理由：

- 它們多半來自 AD 或 Zentera 原始資料
- 它們常同時扮演來源事實欄位與關聯判讀依據
- 一旦在平台任意修改，容易破壞可追溯性

### 14.4 條件式唯讀欄位

以下欄位建議先維持唯讀，除非後續明確定義人工覆寫模型：

- `Role`
  - 目前報告指出此欄位可能由 `VM HostName` 推導
  - 若開放編輯，需區分：
    - `role_inferred`
    - `role_overridden`
  - 否則會讓使用者無法分辨原始推導值與人工覆寫值

### 14.5 建議的第一版最小白名單

如果要先保守落地，建議第一版只開放以下 3 到 4 個欄位：

- `NEW VM`
- `Template Name`
- `Location`
- `NAS Folder Name`

這組白名單的優點是：

- 不直接碰來源主資料
- 不影響主要 join 關係
- 足以支撐交付前人工整理
- 權限與審計模型較容易落地
