## 一、業務背景與問題

電子業 IT 部門需要對內部同仁使用的虛擬機（VM）做兩件事：**管理**（誰用哪台機器、權限、上限人數）與**展示**（讓維運人員與申請人查得到現況）。在這套系統出現之前，這些資訊分散在三個地方：

1. **Helpdesk 工單** — 同仁申請 VM 使用權限時填寫的維運工單（DDP 工單）。
2. **AD / LDAP** — 公司帳號、部門、主管歸屬等身分資料的權威來源。
3. **Zentera 匯出的 Excel/CSV** — VM 主機、角色、應用程式的對應總表，過去以人工維護的總表 + notebook 方式處理。

三邊資料脫節，導致總表更新仰賴人工比對、版本容易對不齊，且新人／離職／轉調時沒有自動化的更新路徑。

**VM Master** 是本專案目前的核心模組，目標是把這三邊資料收斂成一張「可查詢、可維護、可追溯」的 VM 總表，並提供操作人員一個網頁介面直接查看與維護，而不必再手動比對 Excel。

## 二、目前系統能做什麼（功能總覽）

| 功能 | 說明 | 使用情境 |
|------|------|----------|
| **VM 總表查詢**（依 BG 分組） | 網頁上依事業群（BG）分組顯示所有使用者—VM 對應關係，含使用者資料、群組、角色、VM 名稱、單機上限人數等欄位 | 維運人員日常查詢「這個 BG 底下有誰用哪些機器」 |
| **手動編輯 + 發布** | 可在網頁上直接編輯既有列（使用者資料、群組/角色、VM 名稱、單機上限），暫存為草稿，確認無誤後一次「發布」寫回資料庫 | 少量、臨時性的欄位修正（例如單機人數上限調整） |
| **Excel 匯入** | 上傳 Excel 活頁簿，系統自動解析所有工作表，讓操作人員對應欄位後批次匯入。匯入時會自動用 AD 資料補齊缺漏欄位，並依申請人主管的既有 VM 指派推斷應該分配的機器 | 大量、批次性的總表更新（例如整批新進人員或部門異動） |
| **Helpdesk 工單同步** | 直接從 Helpdesk 抓取 DDP 工單，解析內容、串接 AD 補齊身分資料，並自動推斷應分配的 VM，寫入總表 | 承接既有的工單驅動流程，讓工單處理結果自動反映到總表 |
| **執行歷程紀錄** | 每一次「Excel 匯入」或「Helpdesk 同步」都會留下執行紀錄，包含成功/失敗筆數、警告訊息、抽樣列細節 | 事後追查「這次匯入到底改了什麼、哪些列失敗」 |

**一句話說明給主管聽：** 現在同仁在網頁上就能看到最新的 VM 總表；批次異動（Excel/工單）會自動補齊身分與權限欄位再寫入總表；少量修正可以直接在網頁上編輯後發布；每一次異動都有紀錄可查。

## 三、系統架構（業務視角，非技術細節）

系統採用「**查詢與異動分流**」的設計：

- **查詢面**：網頁上看到的總表，只從資料庫的「彙總視圖」讀取，不會被進行中的編輯草稿影響。
- **異動面**：無論是手動編輯發布、Excel 匯入，還是 Helpdesk 同步，都各自走獨立的「指令」通道；系統會把異動內容連同異動前後的差異一起寫入資料庫的同一筆交易，確保「改了就有紀錄，不會半套」。

這個設計的好處是：**看資料的人不會被正在進行的異動干擾，而每一筆異動都可以回溯「改之前是什麼、改之後是什麼」。**

```
Helpdesk 工單 ──┐
AD / LDAP    ──┼─→ 補齊身分與主管歸屬 ──┐
Excel 批次   ──┘                        ├─→ VM 總表（資料庫）──→ 網頁查詢畫面
手動編輯（網頁）───────────────────────┘         ↑
                                         每次異動留下執行紀錄／稽核紀錄
```

## 四、目前所處階段與已知限制

這套系統目前仍是**內部概念驗證（PoC）階段的工具**，尚未具備正式對外系統的一些基本能力：

- **沒有登入或權限機制**：目前任何能連到系統的人都能查看與編輯總表，沒有「誰能看、誰能改」的區分，也沒有記錄「實際是誰做了這次修改」（目前操作紀錄上的異動人是系統寫死的字串，不是真實登入者）。
- **只能以開發模式運行**：目前系統的後端功能是掛載在前端開發伺服器上運行，還沒有獨立的正式後端服務，代表現階段還無法用一般「正式上線」的方式部署（詳見內部技術優化報告）。
- **只能編輯既有資料列**：目前網頁編輯功能只能修改既有的使用者—VM 對應，還不能新增或刪除一整筆對應關係；如果要新增/刪除，仍需透過 Excel 匯入或 Helpdesk 同步。
- **沒有簽核/審批流程**：發布異動不需要第二人確認，這對小量修正沒問題，但若未來異動量變大、影響範圍變廣，可能需要加上審核機制。
- **內部資料傳輸目前未加密**：系統查詢 AD 身分資料時，目前走的是未加密的內部連線，屬於「同網段內可信任」的假設下可接受的做法，但若未來系統需要跨網段部署或有更高的資安稽核要求，這一段需要改成加密連線（技術細節見內部技術優化報告）。

這些限制目前對「內部小範圍試用」是可接受的，但若要推廣到更大範圍或當作正式營運系統，需要在下一階段補齊。

## 五、後續可拓展方向（給決策參考）

| 方向 | 業務價值 | 概略優先序 |
|------|----------|------------|
| **使用者權限與登入機制** | 區分「可查看」與「可編輯」角色，並讓每筆異動都能追溯到真實操作者，是正式上線前的必要條件 | 高 |
| **正式部署（脫離開發模式）** | 讓系統可以穩定運行、可監控、可交由維運團隊接手，而不依賴開發環境 | 高 |
| **新增/刪除 VM 對應的網頁操作** | 補齊目前「只能改，不能增刪」的缺口，減少對 Excel 匯入的依賴 | 中 |
| **簽核／審批流程** | 若未來異動量或影響範圍擴大，加上二次確認可降低誤操作風險 | 中（視使用規模而定） |
| **與其他系統整合（訊息佇列／事件通知）** | 目前的異動紀錄機制已預留欄位供未來對接訊息佇列，可讓其他系統（例如通知、審計、報表）即時感知 VM 總表的變化 | 中長期 |
| **離職／組織異動自動偵測** | 目前身分補齊靠 AD 查詢，若能主動偵測離職或轉調並提示總表需要更新，可減少人工巡檢 | 中長期 |

## 六、建議下一步（給 PM 決策）

1. **先決定使用範圍**：目前系統適合作為「內部維運人員的輔助工具」試用，若要開放給更多人（例如一般申請人自助查詢），建議先補上權限機制。
2. **評估是否需要正式部署**：如果試用效果良好、要進入下一階段推廣，需要安排一次「脫離開發模式、走正式後端服務」的技術投入（細節見內部技術優化報告）。
3. **確認資料範圍是否足夠**：目前總表整合了 Helpdesk 工單、AD、Zentera 三邊資料；如果業務上還需要其他資料源（例如資產管理系統），需要及早提出以評估整合方式。
4. **收集操作人員回饋**：目前「手動編輯」「Excel 匯入」都是新功能，建議先讓實際維運人員試用一輪，確認流程是否符合日常操作習慣，再決定是否投入新增/刪除、審批流程等後續功能。
